A Practical Git Workflow for Growing Development Teams

Oct 24, 2024 • Tekers Engineering Team

When you're coding alone, Git feels like a simple "save button" with superpowers. You write code, commit it, push it, and everything just works. But the moment you add a second or third person to the mix, things get… interesting.

Suddenly, you can't push because "remote contains work you don't have." You merge a branch and half your code disappears. Your teammate breaks the main site while you're asleep. This is where teams struggle—not because Git is broken, but because they lack a workflow.

At Tekers, we believe engineering should be calm, not chaotic. Here is the exact workflow we use to keep our team moving fast without breaking things.

1. Git Basics (For Absolute Beginners)

Before we dive into the workflow, let's make sure we speak the same language. If you just installed Git, here is what you need to know:

  • Repository ("Repo"): The folder where your project lives. Think of it as the project folder, plus a hidden database of every change ever made.
  • Branch: A parallel version of your code. You can create a branch to test an idea without messing up the main project.
  • Commit: A snapshot of your code at a specific moment. It's like a save point in a video game.
  • Origin: The version of your project that lives on the internet (GitHub, GitLab, Bitbucket). It's the central hub.

2. The Role of the Main Branch

In a team, the main branch is sacred.

Rule #1: Never work directly on main.

The main branch should always be deployable. If a new developer joins the team and clones the repo, the code in main must work immediately. If you push broken code to main, you block everyone else from working.

3. Creating a Feature Branch

Every time you start a task—whether it's building a login form or fixing a typo—you create a new home for that work. We call this a "Feature Branch."

Step 1: Go to the main branch and make sure it's up to date. 

git checkout main
git pull origin main

Step 2: Create your new branch. Give it a descriptive name so we know what it does. 

git checkout -b feature/login-page

Now you are in a safe sandbox. You can delete files, break things, and experiment without hurting anyone else.

4. Daily Work Routine

You've written some code. Now what? You need to save your progress.

Don't wait until the end of the week to commit. Commit often. Small commits are easy to understand and easy to fix if something goes wrong.

How to Commit Properly

# 1. Check which files you changed
git status

# 2. Add files to the staging area
git add .

# 3. Save the snapshot with a message
git commit -m "Add email validation to login form"

Writing Good Commit Messages

"Update code" is a useless message. Write for humans. Explain what you did and why.

  • ❌ Fixed it
  • ❌ WIP
  • ✅ Fix navigation bar overlap on mobile screens

Once you have committed your work, push it to the cloud so your team can see it (and so you have a backup!). 

git push origin feature/login-page

5. Understanding Merge

"Merging" is simply taking the history of two branches and combining them.

When you are done with your feature, you want to bring your changes back into main. Usually, you do this via a "Pull Request" on GitHub/GitLab, but understanding the command is vital. 

# 1. Switch back to main
git checkout main

# 2. Update main (someone else might have pushed while you were working)
git pull origin main

# 3. Merge your feature into main
git merge feature/login-page

What is a "Conflict"?

A conflict happens when two people change the exact same line of code in different ways. Git is smart, but it can't read minds. It stops and asks you: "Which version do you want to keep?"

Don't panic. Open the file, look for the markers (<<<<<<<), pick the correct code, and commit the fix.

6. Common Mistakes to Avoid

  • Working on main: We said it before, but it bears repeating. Don't do it.
  • Huge Commits: Changing 50 files in one commit makes it impossible to review. Keep it small.
  • Ignoring Updates: Always git pull before you start your day. If you work on old code, you guarantee conflicts later.
  • Vague Messages: Be specific. Your future self will thank you.

7. The Tekers Workflow Summary

To keep our team happy and our code clean, we follow these simple rules:

  1. Always pull main before starting.
  2. One task = One branch.
  3. Commit often with clear messages.
  4. Push your branch to backup your work.
  5. Merge only when the feature is complete and tested.

Git is a tool for communication. Use it to tell a clear story about how your software is evolving.
